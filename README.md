# squid-proxy-n8n

Локальный Squid для n8n с автоматически обновляемым пулом внешних прокси.

```text
n8n -> локальный Squid -> внешний прокси из proxy.txt -> api.telegram.org
                     |
                     +-> напрямую с сервера -> остальные HTTPS API
```

Один экземпляр предназначен для одного клиента. У каждого клиента свои `.env`, `config/proxy.txt` и Docker-сеть. Комплект не изменяет workflow и не обращается к Docker socket. Порт прокси на хост не публикуется, Traefik для исходящих запросов не нужен.

## Требования

- Linux-сервер, Docker Engine, Docker Compose v2 с поддержкой `up --wait`, Make.
- Существующая Docker-сеть, в которой доступны n8n и его workers.
- Внешние HTTP/HTTPS-прокси с поддержкой CONNECT. SOCKS5 не поддерживается.

Образ собирается на Alpine 3.23 со Squid 7 и Python из системных пакетов. У менеджера нет Python-зависимостей за пределами стандартной библиотеки.

## Первый запуск

```bash
git clone https://github.com/ditarget/squid-proxy-n8n.git
cd squid-proxy-n8n
make init
```

`make init` создает `.env` и пустой `config/proxy.txt`. Существующие файлы не перезаписываются. Без корректного непустого списка прокси запуск завершится ошибкой.

Узнай имя сети n8n и ее подсеть:

```bash
docker network ls
docker network inspect traefik_network --format '{{range .IPAM.Config}}{{println .Subnet}}{{end}}'
```

Заполни `.env`, например:

```dotenv
COMPOSE_PROJECT_NAME=squid-proxy-client-a
CLIENT_NETWORK=traefik_network
PROXY_ALIAS=squid-proxy-client-a
ALLOWED_CLIENT_CIDRS=172.20.0.0/16
POLL_INTERVAL=5
RELOAD_TIMEOUT=15
```

`CLIENT_NETWORK` должна уже существовать. `ALLOWED_CLIENT_CIDRS` содержит фактические подсети клиентских контейнеров, через запятую без пробелов. Маски `0.0.0.0/0` и `::/0` запрещены. Доступ предоставляется всей указанной подсети, поэтому для разных клиентов используй отдельные сети. На одном сервере также задай разные `COMPOSE_PROJECT_NAME` и `PROXY_ALIAS` для каждого экземпляра.

Заполни `config/proxy.txt`, по одному прокси на строку:

```text
http://user1:password1@proxy1.example.net:8080
http://user2:password2@proxy2.example.net:3128
https://proxy3.example.net:443
```

Без авторизации можно указывать `http://host:port`. Если порт пропущен, используются 80 для HTTP и 443 для HTTPS. Пустые строки и строки, начинающиеся с `#`, пропускаются. Дубликаты убираются автоматически.

Спецсимволы логина и пароля должны быть URL-encoded. Например, пароль `p@ss%word` записывается как `p%40ss%25word`. У HTTPS-прокси проверяется TLS-сертификат. HTTP-прокси получает Basic-авторизацию без отдельного TLS-шифрования соединения до прокси; HTTPS к самому Telegram остается зашифрованным в обоих случаях.

Файл `.env` и настоящий `config/proxy.txt` исключены из Git, Docker build context и архива поставки. Храни резервную копию списка отдельно с ограниченным доступом.

Запусти комплект:

```bash
make deploy
make health
make status
```

`make deploy` последовательно собирает образ, проверяет список и конфигурацию в отдельном контейнере, затем поднимает сервис и ожидает его локальной готовности. Ошибка предварительной проверки не останавливает уже работающий экземпляр.

## Подключение n8n

Добавь в `environment` основного контейнера n8n и всех workers:

```yaml
HTTPS_PROXY: http://squid-proxy-client-a:3128
https_proxy: http://squid-proxy-client-a:3128
NO_PROXY: localhost,127.0.0.1,::1,postgres,redis,squid-proxy-client-a
no_proxy: localhost,127.0.0.1,::1,postgres,redis,squid-proxy-client-a
```

Если существующий Compose использует список `- KEY=value`, сохрани его формат. Замени имя прокси на свой `PROXY_ALIAS`. В исключения добавь имена остальных внутренних HTTP-сервисов, с которыми работает n8n. Не добавляй `api.telegram.org` в исключения.

Пересоздай контейнеры n8n штатной командой их проекта, чтобы применились переменные. Обычный restart новые значения из Compose не применяет. URL в нодах остаются прежними.

Если в HTTP Request ноде уже заполнено поле Proxy, оно имеет приоритет над глобальными переменными. Для использования общего пула убери такие индивидуальные значения. Собственные скрипты и сторонние ноды могут использовать отдельные HTTP-клиенты, поэтому их поддержку переменных прокси нужно проверять отдельно.

Задается только `HTTPS_PROXY`: обычный HTTP продолжает идти напрямую из n8n. Squid принимает только CONNECT к порту 443. При необходимости HTTPS на других портах нужно явно расширить конфигурацию и проверки.

## Обновление списка

После изменения `config/proxy.txt` менеджер автоматически обнаружит новый список, обычно в течение `POLL_INTERVAL` секунд плюс время проверки и применения. Контейнеры n8n и Squid пересоздавать не нужно.

Рекомендуемый способ обновления - записать новый список в `config/proxy.next`, затем атомарно заменить файл:

```bash
mv config/proxy.next config/proxy.txt
```

В контейнер смонтирована вся папка `config`, поэтому замена файла через rename видна менеджеру. Обновления во время обычного редактирования тоже обнаруживаются, но атомарная замена исключает применение частично записанного корректного списка.

Менеджер проверяет весь список и синтаксис будущей конфигурации, атомарно меняет активный файл, отправляет Squid SIGHUP и проверяет точную версию локальным служебным запросом. Если подтверждение не получено, возвращает предыдущую конфигурацию. Если откат нельзя подтвердить, сервис завершает работу.

Пустой, поврежденный, слишком большой или недоступный новый файл сохраняет последний подтвержденный пул в работающем контейнере. Ошибка отражается в `make status`. После перезапуска контейнера список снова читается с диска: история конфигураций хранится только во временной файловой системе. Для восстановления исправь файл на диске. Предельный размер входного файла - 1 MiB.

Прокси выбираются Squid через round-robin для новых соединений. Открытый туннель закреплен за выбранным прокси. Обрыв туннеля не вызывает перенос или повторную отправку API-запроса менеджером. Для `api.telegram.org` прямой выход запрещен даже при недоступности всего пула.

## Проверки и журналы

```bash
make health
make status
make logs
make check
```

`health` подтверждает работу менеджера, слушающий Squid и точную примененную конфигурацию. Он не проверяет доступность внешних прокси или доставку Telegram-сообщения. `check` проверяет текущий файл в отдельном контейнере и не меняет работающий пул.

В статусе видны количество прокси, digest активного файла, время применения, heartbeat и код последней ошибки обновления. Сырые сообщения Squid и содержимое конфигурации не выводятся: они могут содержать авторизацию. В stdout передаются только события менеджера и строки маршрутизации без URL, заголовков и учетных данных.

Для проверки реального маршрута выполни из n8n запросы к `https://api.telegram.org/botinvalid/getMe` и `https://example.com`. Первый должен дать ответ Telegram об ошибке, второй - ответ сайта. Ответ 404 от Telegram в этой проверке нормален. В журнале соответствующие завершенные туннели показывают маршрут с `PARENT` и `HIER_DIRECT`. Это проверка соединения, а не отправки сообщения.

Обновление самого комплекта на сервере:

```bash
git pull --ff-only
make deploy
make health
```

Пользовательские `.env` и `config/proxy.txt` сохраняются. `make down` останавливает только этот Compose-проект и не удаляет внешнюю сеть.

## Разработка и передача клиентам

```bash
make test
make integration
make package
```

`test` запускает unittest в Alpine-контейнере без сети. `integration` проверяет реальный Squid с локальными фиктивными origin и parent-серверами, также без внешней сети. Проверяются маршруты, запрет прямого Telegram, замена файла на ходу, авторизация и сохранение рабочего пула при ошибках.

Для локальных проверок через Podman:

```bash
make test ENGINE=podman
make integration ENGINE=podman
```

`make package` создает `dist/squid-proxy-n8n.tar.gz` из явного списка файлов, без Git-истории и клиентских настроек. Архив можно распаковать на сервере клиента и начать с `make init`. Все файлы кода короче 400 строк.
